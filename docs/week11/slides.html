Question 1: Student Class

Implementing a class with name, age, and GPA

Key concepts: pass-by-reference, member initializer lists, const correctness

Alright, let's go through the first question of this tutorial. We are asked to implement a Student class with some basic attributes: name, age, and GPA. I'll walk you through the implementation, and along the way, I'll point out some modern C++ practices that will make your code much more robust and efficient.

Part 1: Private Members


private:
  std::string name;
  int age;
  double gpa;

Encapsulation — keeping members private means external code cannot directly access or modify them. It must go through our public interface.

First, let's define the private members. This part is straightforward. We need an std::string for the name, an int for the age, and a double for the GPA. We keep these private to enforce encapsulation.

Part 2: The Constructor

Step 1: Body Assignment


Student(std::string studentName, int studentAge, double studentGPA) {
  name = studentName;
  age = studentAge;
  gpa = studentGPA;
}

The most straightforward approach — just assign values in the body.

Two-step process:

  1. Compiler default-constructs each member (empty string, 0, 0.0)
  2. Then overwrites them with your assignments
The most basic way to initialize members is doing assignments inside the function body. While this works, the compiler first creates the member variables with default values, and then overwrites them. That's two steps where one would suffice.

Part 2: The Constructor

Step 2: Member Initializer List


Student(std::string studentName, int studentAge, double studentGPA)
    : name(studentName), age(studentAge), gpa(studentGPA) {}

One-step process:
Constructs and initializes each member directly. No wasted default construction.

Cleaner, faster, and the standard practice for constructors in C++.

Instead, we use the Member Initializer List. This constructs and initializes the member variables directly in one step. It's cleaner, faster, and the standard practice for constructors in C++.

Part 2: The Constructor

Step 3: Pass by Const Reference


Student(const std::string& studentName, int studentAge, double studentGPA)
    : name(studentName), age(studentAge), gpa(studentGPA) {}
  • int, double — pass by value is fine. Small and cheap to copy.
  • std::string — use const reference to avoid copying the entire string.
  • & avoids the copy. const guarantees we won't modify the original.

This is the approach taught in lectures.

Now let's look at the parameters. For primitive types, pass by value is fine. But for std::string, passing by value creates an unnecessary copy. We use const reference instead — the ampersand avoids the copy, and const guarantees we won't modify the original. This is the approach taught in lectures.

Part 2: The Constructor

Step 4: std::move (Bonus)


Student(std::string studentName, int studentAge, double studentGPA)
    : name(std::move(studentName)), age(studentAge), gpa(studentGPA) {}
  • std::move casts to an rvalue reference — transfers the string's internal buffer instead of copying.
  • Pass by value + std::move: especially efficient when caller passes a temporary like "Alice".

Not covered in lectures — not required for exams.
Included for those who want to understand the final solution.

There's one more approach: pass by value and use std::move. std::move tells the compiler to transfer the string's internal buffer instead of copying. This is not covered in lectures and not required for exams — it's a bonus for those who want to understand the final solution code.

Part 3: Getters

Step 1: Basic Getters


std::string getName() { return name; }
int getAge() { return age; }
double getGPA() { return gpa; }

The simplest approach — just return the values. This works, but we can do better.

Now, let's implement the getters. The primary job of a getter is to read data without modifying the object. The simplest approach is to just return the values. This works, but we can improve it.

Part 3: Getters

Step 2: const Member Functions


std::string getName() const { return name; }
int getAge() const { return age; }
double getGPA() const { return gpa; }
          

std::string getName() const;
//                    ^^^^^

This is const correctness — guarantees to the compiler that
calling this method will not alter the internal state of the class.

Notice the const keyword at the end of the function signature. This is called const correctness. It guarantees to the compiler that calling this method will not alter the internal state of the class.

Why Does const Matter?


class A {
 private:
  int a;
 public:
  A(int a = 0) : a(a) {}
  int getA() const { return a; }
};

int main() {
  const A a(0);       // a is a CONST object
  std::cout << a.getA() << std::endl;  // OK: getA() is const
  return 0;
}

If you declare a const object, the compiler will only allow you to call methods marked as const. If you forget const on your getter, the compiler throws an error.

Bonus: look into the mutable keyword for exceptions to this rule (out of scope for today).

Why does this matter? If you declare a const object, the compiler will only allow you to call methods marked as const. If you forget to add const to your getter, the compiler will throw an error. If you want to dive deeper, you can look into the mutable keyword, but that's out of scope for today.

Part 3: Getters

Step 3: Return by Const Reference


const std::string& getName() const { return name; }
int getAge() const { return age; }
double getGPA() const { return gpa; }
  • int, double — return by value is fine. Small types that fit into CPU registers.
  • std::string — returning by value copies the entire string every time. Use const std::string& to return a reference without copying.
For primitive types, returning by value is fine. But for std::string, returning by value copies the entire string every time the getter is called. We can return a const reference instead to avoid the copy. The const on the return type prevents the caller from modifying the string through this reference.

Part 4: Setters

Setters modify the state — not marked const


void setName(std::string studentName) { name = std::move(studentName); }
void setAge(int studentAge) { age = studentAge; }
void setGPA(double studentGPA) { gpa = studentGPA; }
  • setName: same pass by value + std::move pattern from the constructor.
  • setAge, setGPA: primitives — simple assignment is all we need.
Finally, the setters. For setName, we use the same pass by value + std::move pattern from the constructor. For the primitive types, simple assignment is all we need. Note that setters are not marked const, because they inherently modify the object.

Complete Solution


#include <iostream>
#include <string>

class Student {
 private:
  std::string name;
  int age;
  double gpa;

 public:
  Student(std::string studentName, int studentAge, double studentGPA)
      : name(std::move(studentName)), age(studentAge), gpa(studentGPA) {}

  void displayDetails() const {
    std::cout << "Student Name: " << name << std::endl;
    std::cout << "Age: " << age << std::endl;
    std::cout << "GPA: " << gpa << std::endl;
  }

  const std::string& getName() const { return name; }
  int getAge() const { return age; }
  double getGPA() const { return gpa; }

  void setName(std::string studentName) { name = std::move(studentName); }
  void setAge(int studentAge) { age = studentAge; }
  void setGPA(double studentGPA) { gpa = studentGPA; }
};
Alright, that covers the full implementation. We've set up the constructor efficiently, enforced const correctness on our getters, and implemented our setters.

Q1: Key Takeaways

  • Pass by value + std::move when you need to store a std::string
  • Member initializer list directly constructs members in one step — preferred over body assignment
  • Trailing const on getters guarantees they don't modify object state
  • Return by const reference for non-trivial types; by value for primitives
  • Pass by value + std::move is a common setter idiom for strings

Question 2: Copy Constructor

Identifying issues in the VisitorCounter class

Now let's move on to question 2. This question is about understanding what happens when you copy an object that manages dynamic memory, and why you need a custom copy constructor.

The Setup


class VisitorCounter {
private:
    int* count; // Pointer to dynamically allocated memory
public:
    VisitorCounter(int initialCount) {
        count = new int(initialCount); // allocates on heap
    }
    ~VisitorCounter() { delete count; }
    void increment() { (*count)++; }
    void display() const {
        cout << "Visitor Count: " << *count << endl;
    }
    // No copy constructor defined!
};
          

VisitorCounter counter(10);
VisitorCounter counterCopy = counter;  // What happens here?
counterCopy.increment();
counterCopy.increment();
counter.display();  // What does this print?
Here's the VisitorCounter class — it has a pointer member managed with new and delete, but no copy constructor. The question is: when we copy counter and increment the copy, what happens to the original?

What Does the Default Copy Constructor Do?

No copy constructor defined → compiler generates a default one


// Compiler-generated default copy constructor:
VisitorCounter(const VisitorCounter& other) {
    count = other.count;  // Copies the VALUE of the pointer
}

C++ copies every member's value. For a pointer, its value is the address — so both pointers end up holding the same address.

Since no copy constructor is defined, the compiler generates a default one. The default copy constructor copies every member's value — this is all C++ ever does. But here's the key insight: a pointer's value IS an address. So copying the pointer's value means both objects now store the same address and therefore point to the same memory on the heap.

Default Copy: Step by Step

Step 1: Before the copy — VisitorCounter counter(10);

counter.count stores the address 0xA00, pointing to the integer 10 on the heap.

Before the copy, counter has a pointer member count whose value is the address 0xA00. On the heap at that address, there's an integer with value 10.

Default Copy: Step by Step

Step 2: Copy the pointer's value — VisitorCounter counterCopy = counter;

Stack

counterCopy
count: 0xA00
→
Heap
0xA00

The pointer's value (0xA00) is copied — so both pointers now point to the same heap memory!

The default copy constructor copies the value of each member. The value of counter.count is 0xA00 — that's an address. So counterCopy.count also gets the value 0xA00. Now both pointers hold the same address, meaning they point to the exact same integer on the heap. No new memory was allocated — the data itself was never copied.

Issue 1: Unintended Sharing


counterCopy.increment();  // (*count)++ → 11
counterCopy.increment();  // (*count)++ → 12
Stack
counter
count: 0xA00
counterCopy
count: 0xA00
→
Heap
0xA00
12

counter.display() also prints 12!
Modifying the copy unexpectedly changes the original.

When we increment the copy, it modifies the value at 0xA00. But since counter also points to 0xA00, counter.display() now shows 12 as well. Modifying the copy unexpectedly changes the original!

Issue 2: Double Free

When main() ends, destructors run in reverse order:

  1. counterCopy destructor: delete count; — frees 0xA00 ✓
  2. counter destructor: delete count; — frees 0xA00 again!

Undefined Behavior!
Double free can cause crashes, memory corruption, or security vulnerabilities

When main ends, destructors run in reverse order. counterCopy's destructor deletes the memory at 0xA00. Then counter's destructor tries to delete the same memory again — that's a double free, which is undefined behavior.

Summary of Issues

Root cause: The default copy constructor copies the pointer's value (an address), not the pointed-to data. Both objects end up pointing to the same memory.

  1. Unintended Sharing — modifying one object affects the other
  2. Double Free — both destructors delete the same memory
  3. No Copy Assignment Operator — a = b; would have the same issues
To summarize: the root cause is that the default copy constructor copies the pointer's value — which is just an address. This leads to unintended sharing, double free, and the same problems would also apply to copy assignment.

The Fix: Deep Copy Constructor


VisitorCounter(const VisitorCounter& other) {
    count = new int(*other.count);  // Allocate NEW memory, copy the VALUE
    cout << "Copy constructor called with count "
         << *count << endl;
}
Stack
counter
count: 0xA00
counterCopy
count: 0xB00
Heap
0xA00
10
0xB00
10

Now each object has its own memory — copying the pointer's value alone isn't enough, we must also copy the pointed-to data.

The fix is to write a custom copy constructor. Instead of just copying the pointer's value (the address), we allocate new memory and copy the pointed-to data. Now each object has its own memory on the heap — completely independent.

Also Fix: Copy Assignment Operator


VisitorCounter& operator=(const VisitorCounter& other) {
    if (this != &other) {          // Self-assignment check
        *count = *other.count;     // Copy the VALUE
    }
    return *this;
}

Without this, a = b; would still only copy the pointer's value

We also need a copy assignment operator. Without it, using the equals sign to assign one object to another would still only copy the pointer's value — the same problem. Notice the self-assignment check to handle the edge case of a = a.

The Rule of Three

If a class needs any one of these, it probably needs all three:

  1. Destructor — clean up resources
  2. Copy Constructor — deep copy on initialization
  3. Copy Assignment Operator — deep copy on assignment

If your class manages a resource (heap memory, file handle, etc.), you need all three!

This leads to the famous Rule of Three: if your class needs a custom destructor, copy constructor, or copy assignment operator, it almost certainly needs all three. This applies whenever your class manages a resource like heap memory.

Complete Fixed Class


class VisitorCounter {
private:
    int* count;

public:
    // Constructor
    VisitorCounter(int initialCount) {
        count = new int(initialCount);
        cout << "Constructor called with the count as "
             << *count << endl;
    }

    // Copy Constructor (DEEP COPY)
    VisitorCounter(const VisitorCounter& other) {
        count = new int(*other.count);
        cout << "Copy constructor called with count "
             << *count << endl;
    }

    // Copy Assignment Operator
    VisitorCounter& operator=(const VisitorCounter& other) {
        if (this != &other) {
            *count = *other.count;
        }
        return *this;
    }

    // Destructor
    ~VisitorCounter() {
        cout << "Destructor called with the count being "
             << *count << endl;
        delete count;
    }

    void increment() { (*count)++; }
    void display() const {
        cout << "Visitor Count: " << *count << endl;
    }
};
Here's the complete fixed class with all three members of the Rule of Three: constructor, copy constructor with deep copy, copy assignment operator, and destructor.

Default Copy vs Custom Copy

Default (copy pointer value) Custom (copy pointed-to data)
What's copied The address (0xA00) The data (10) into new memory
Result Two pointers → same memory Two pointers → separate memory
Modify copy Affects original No side effects
Destruction Double free! Safe cleanup
Here's the comparison. The default copy constructor copies the pointer's value — the address — so both objects point to the same memory. A custom copy constructor allocates new memory and copies the pointed-to data, so each object is independent.

Q2: Key Takeaways

  • The default copy constructor copies every member's value — for a pointer, that value is an address
  • If your class uses new, you need a custom copy constructor that also copies the pointed-to data
  • Remember the Rule of Three: destructor + copy constructor + copy assignment
  • Always test: does copying an object cause unexpected sharing or crashes?
To wrap up Q2: the default copy constructor copies member values. For pointers, that value is just an address, so both objects end up pointing to the same memory. If your class uses new, write a custom copy constructor that allocates new memory and copies the data. And remember the Rule of Three.

The Modern Alternative: Smart Pointers

What if we could avoid manual new/delete entirely?

C++11 introduced smart pointers in <memory>
They automatically manage the lifetime of heap-allocated objects

  • std::unique_ptr — sole ownership, cannot be copied, only moved
  • std::shared_ptr — shared ownership via reference counting
Now let me show you the modern C++ way to solve this entire category of problems. C++11 introduced smart pointers that automatically manage heap memory. unique_ptr gives exclusive ownership — when it goes out of scope, the memory is freed. shared_ptr allows multiple owners through reference counting.

Rewrite with unique_ptr


#include <memory>

class VisitorCounter {
private:
    std::unique_ptr<int> count;

public:
    VisitorCounter(int initialCount)
        : count(std::make_unique<int>(initialCount)) {}

    void increment() { (*count)++; }

    void display() const {
        std::cout << "Visitor Count: " << *count << std::endl;
    }
};

No destructor needed — unique_ptr auto-deletes
No copy constructor needed — copying is blocked at compile time
No double free possible — only one owner

Here's the VisitorCounter rewritten with unique_ptr. Notice how much simpler it is — no destructor, no copy constructor, no assignment operator. unique_ptr automatically deletes the memory when the object is destroyed. And since unique_ptr cannot be copied, the compiler prevents accidental pointer-value-only copies at compile time. If you need to copy, you'd explicitly write a custom copy constructor — but the default behavior is safe.

When You Need Sharing: shared_ptr


std::shared_ptr<int> p1 = std::make_shared<int>(42);
std::shared_ptr<int> p2 = p1;  // Both own the same data

std::cout << p1.use_count();   // 2
// p1 and p2 both point to the same int(42)

// Memory freed only when LAST shared_ptr is destroyed

Reference counting: tracks how many shared_ptrs point to the same object
Memory is freed only when the count reaches zero — no double free!

If you actually need multiple objects to share the same data, use shared_ptr. It uses reference counting — each copy increments the count, each destruction decrements it, and the memory is only freed when the last shared_ptr is destroyed. No manual tracking needed, no double free.

Raw Pointer vs Smart Pointers

Raw Pointer unique_ptr shared_ptr
Ownership Unclear Exclusive Shared
Copyable? Yes (address only) No (move only) Yes (ref count)
Auto cleanup? No Yes Yes
Double free? Possible Impossible Impossible

Modern C++ guideline: prefer smart pointers over raw new/delete

Here's a comparison. Raw pointers have unclear ownership, and copying only copies the address — not the data. unique_ptr has exclusive ownership and blocks copying. shared_ptr allows safe sharing with reference counting. The modern C++ guideline is clear: prefer smart pointers over raw new and delete.

Question 3: Pen Class

this operator and method chaining

Key concepts: the this pointer, returning *this, method chaining

Let's move on to question 3. This one is about the this pointer and method chaining. We need to implement a Pen class where setters return a reference to the current object, enabling us to chain multiple method calls together.

What is this?

Every non-static member function has access to a special pointer: this


myPen.setColor("Red");
// Inside setColor:
//   this   → pointer to myPen
//   *this  → the myPen object itself

this is a pointer to the current object
*this dereferences it — giving us the object itself

In C++, every non-static member function has access to a special pointer called this. It points to the current object — the one on which the method was called. So if we call myPen.setColor, inside that function, this is a pointer to myPen, and *this is myPen itself.

Method Chaining


// Without chaining:
myPen.setColor("Red");
myPen.setPrice(2.0);
myPen.display();

// With chaining:
myPen.setColor("Red").setPrice(2.0).display();

If a setter returns *this (a reference to the current object),
we can immediately call another method on it!

The return type must be Pen& (reference), not Pen (copy)

The idea behind method chaining is: if a setter returns *this — a reference to the current object — we can immediately call another method on the returned reference. This lets us write compact, readable code. The return type must be a reference, not a copy, so that each chained call operates on the same object.

How It Works


myPen.setColor("Red").setPrice(2.0).display();
  1. myPen.setColor("Red") → sets color to "Red", returns *this (which is myPen)
  2. .setPrice(2.0) → called on the returned reference, sets price to 2.0, returns *this
  3. .display() → called on the returned reference, prints the pen details

Each setter returns the same object, so the next call in the chain operates on it

Let's trace through the chain step by step. First, setColor is called on myPen, sets the color, and returns *this — which is myPen. Then setPrice is called on that returned reference, sets the price, and returns *this again. Finally display is called on the same reference, and prints the details. Each call operates on the same myPen object.

Implementing the Setters


Pen& setColor(std::string newColor) {
  color = newColor;
  return *this;  // Return the current object by reference
}

Pen& setPrice(double newPrice) {
  price = newPrice;
  return *this;
}
  • Return type is Pen& — a reference to the same object
  • return *this; — returns the current object, enabling the next chained call
Here are the setters. Both set the member variable, then return *this. The return type Pen& means we're returning a reference — not a copy — so the next method in the chain operates on the exact same Pen object.

Implementing display()


void display() const {
  std::cout << "Color: " << color << std::endl;
  std::cout << "Price: $" << price << std::endl;
}
  • Returns void — it's the end of the chain
  • Marked const — it only reads the object's state
The display method simply prints the color and price. It returns void since it's the end of the chain. And it's marked const because it doesn't modify the object.

Complete Solution


#include <iostream>
#include <string>

class Pen {
 private:
  std::string color;
  double price;

 public:
  Pen(std::string initialColor, double initialPrice) {
    color = initialColor;
    price = initialPrice;
  }

  Pen& setColor(std::string newColor) {
    color = newColor;
    return *this;
  }

  Pen& setPrice(double newPrice) {
    price = newPrice;
    return *this;
  }

  void display() const {
    std::cout << "Color: " << color << std::endl;
    std::cout << "Price: $" << price << std::endl;
  }
};
Here's the complete solution. The setters return *this to enable chaining, and display is a const method that ends the chain.

Q3: Key Takeaways

  • this is a pointer to the current object; *this dereferences it
  • Method chaining: setters return *this so calls can be chained
  • Return type must be Pen& (reference) — not Pen (copy)
  • The chain's last method (like display()) can return void

Question 4: Box Class

Friend functions

Key concept: friend functions — external functions that can access private members

Now let's look at question 4. This one introduces friend functions — a way to give a non-member function access to a class's private members. We need to implement a Box class with a friend function that displays the box dimensions.

What is a Friend Function?

A friend function is a non-member function that is granted access to a class's private and protected members.

  • Declared with friend keyword inside the class
  • Defined outside the class — no Box:: prefix
  • Called like a regular function: displayDimensions(myBox), not myBox.displayDimensions()
  • Does not have a this pointer — must receive the object as a parameter
A friend function is a regular standalone function that has been granted special access to a class's private members. You declare it with the friend keyword inside the class, but define it outside. It's called like a normal function, not as a member. And since it's not a member, it doesn't have a this pointer — it must receive the object as a parameter.

Step 1: Declare the Friend


class Box {
  // ... private members and constructor ...

  friend void displayDimensions(const Box& box);
};

This tells the compiler: "displayDimensions is allowed to access my private members"

The friend keyword only appears in the declaration inside the class

First, we declare the friend function inside the class. This single line tells the compiler that displayDimensions is allowed to access Box's private members. Note that the friend keyword only appears here — not in the function definition.

Step 2: calculateVolume()


void calculateVolume() {
  std::cout << "Box Volume: " << length * width * height
            << " cubic units" << std::endl;
}

This is a regular member function — it can access private members directly via this

calculateVolume is a regular member function — it has access to private members through the this pointer, so it can directly use length, width, and height to compute the volume.

Step 3: Define the Friend Function


void displayDimensions(const Box& box) {
  std::cout << "Box Dimensions: " << std::endl;
  std::cout << "Length: " << box.length << std::endl;
  std::cout << "Width: "  << box.width  << std::endl;
  std::cout << "Height: " << box.height << std::endl;
}
  • No Box:: prefix — it's not a member function
  • Accesses box.length, box.width, box.height directly — allowed because it's a friend
  • Takes const Box& — receives the object by reference, won't modify it
The friend function is defined outside the class, with no Box:: prefix. Even though length, width, and height are private, it can access them through the box parameter because it was declared as a friend. We pass by const reference since we only need to read the data.

Member Function vs Friend Function

Member Function Friend Function
Private access? Yes (via this) Yes (via passed object)
Call syntax myBox.calculateVolume() displayDimensions(myBox)
Has this? Yes No
Defined with Box::? Yes No
Here's a comparison. Both can access private members, but they differ in how: member functions use this, friend functions receive the object as a parameter. Member functions are called on the object, friend functions take the object as an argument.

Complete Solution


#include <iostream>

class Box {
 private:
  double length;
  double width;
  double height;

 public:
  Box(double l, double w, double h) {
    length = l;
    width = w;
    height = h;
  }

  void calculateVolume() {
    std::cout << "Box Volume: " << length * width * height
              << " cubic units" << std::endl;
  }

  friend void displayDimensions(const Box& box);
};

void displayDimensions(const Box& box) {
  std::cout << "Box Dimensions: " << std::endl;
  std::cout << "Length: " << box.length << std::endl;
  std::cout << "Width: "  << box.width  << std::endl;
  std::cout << "Height: " << box.height << std::endl;
}
Here's the complete solution. The friend declaration is inside the class, the friend function definition is outside. calculateVolume is a regular member function.

Q4: Key Takeaways

  • friend grants a non-member function access to private members
  • Declared inside the class, defined outside (no Box:: prefix)
  • Called like a regular function, not on an object
  • Use const reference to avoid copying and prevent modification
